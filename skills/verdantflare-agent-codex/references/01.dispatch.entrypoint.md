# Codex 跨智能体派单与结果回收（01.dispatch）

## 1. 输入与输出

- **输入**：明确的工作目录绝对路径 `cwd`、新的 `request_id`、明确的 `mode`（`plugin` 或 `managed`）、包含目标/允许修改路径/输入材料/禁触内容/验证命令/完成标准的 `prompt`；`plugin` 模式另传 `thread_id`；续接与取消传入 `task_id` 与 `expected_turn_id`。
- **输出**：持久任务编号 `task_id`、会话与轮次编号、增量事件流、待处理审批链接 `pending[].approval_url` 或分页 `content_json` 结果。
- **公共依据**：[公共规则](00.common.rules.md)、[技能入口](../SKILL.md)。

## 2. 分类

将有明确工作目录、输入、修改范围和验收标准的任务交给 Codex，适用于代码实现、验证、排障与受授权的本地工作区操作。方案不明确时先由上游澄清，不通过执行智能体替用户决定产品边界。

- **`plugin`**：用户指定已打开的 Codex 插件会话；能力查询须显示持有者可达，且派单前确认会话空闲，不会创建新插件标签页。不同 `thread_id` 可并行，目录重叠不再构成拒绝理由，仍要求各自持有者可达和权限来源可确认。
- **`managed`**：调用者明确选择独立 App Server；创建新的后端会话并复用本机认证，不承诺插件 UI 自动显示。

`codex_capabilities` 返回版本、会话摘要、持有者可达性和分页游标。查询结果只代表当时可达，写操作仍会重新检查。新运行时返回 `plugin_concurrency.scope=thread`、`recovery_protocol=thread-recovery-v1` 和固定于模块导入时的 `service_build`；须同时核对 `verified` 与清单摘要，磁盘安装并不证明既有进程已加载。`read_verified` 只证明读取；任务执行结果由具体任务证据判断。

## 3. 工作流

### 3.1 接入检查与安装校验

确认服务已安装，宿主 MCP 列表包含 `verdantflare-agent-codex`。配置入口由 `VERDANTFLARE_AGENT_CODEX_SERVICE` 指定，默认从用户数据目录的 `verdantflare-agent-codex/service.json` 读取。Python 启动器只读取配置并调用安装好的服务，不在调用时下载依赖。运行 `codex_capabilities`，必要时传入 `cwd` 与分页 `cursor`；选择用户指定的会话编号。找不到在线持有者时让用户打开该会话，不自行改派其他用户会话。

安装前先执行 `python scripts/generate_build.py` 生成确定性运行清单；核对维护源、安装副本与实际连接进程的 `service_build`。清单 `verified=false` 或旧进程缺少标识时，不报告新版本已加载。版本切换等待在途任务安全窗口，不混跑新旧租约语义。

### 3.2 面板打开、会话创建命名与派单

- **兄弟会话打开与本地套接字窗口**：从当前 VS Code Codex 会话派兄弟任务时，使用宿主原生协作创建和续派。获取兄弟线程的原生 Session ID 后，使用 `scripts/open_panel.py <当前项目目录> --session <Session ID>` 在同一个窗口打开它（沿当前 Codex App Server 进程树定位扩展宿主，由配套扩展核对项目和会话标签，返回的 `opened=true` 证明标签已打开，任务状态和回复仍从原生协作通道读取，适用于已安装配套扩展的 Windows VS Code 桌面窗口）。对使用本地套接字的 Windows 项目窗口，先用 .NET 8 SDK 构建 `resources/panel-transport/PanelTransport.csproj`；安装器 `--panel-transport` 接收 JSON 文件（`client` 指向 `PanelTransport.exe`，`hosts` 每项填项目绝对路径 `cwd` 与当前用户私有目录内套接字绝对路径 `socket`，构建产物连同旁边的运行文件保留在稳定位置）。使用 `scripts/open_panel.py <项目目录> --code <Code.exe路径>` 打开窗口（非默认安装加 `--config <运行目录/config.json>`），首次打开后在插件中选择所需权限，再用 `codex_session_create` 取得面板 Session ID 并通过 `codex_capabilities` 核对其归属和权限；关闭窗口即可结束连接。
- **专用会话权限一致性与路由**：需在面板查看并通过插件派单的专用会话，创建时须与宿主显式权限选择一致。`managed` 创建使用自身配置，任务参数不能指定或覆盖权限；不能保证一致时，创建后只走原受管路径，不在面板接管。已授权且权限一致时，才可通过 VS Code 的 `vscode://openai.chatgpt/local/<thread_id>` 路由打开并查询持有者（依赖宿主版本，不等于 MCP start 支持新建插件标签，不保证其他 App Server 能恢复，不得自动选择无关用户会话）。派单前查看 `threads[].permission_alignment`（`match` 一致、`conflict` 至少一项不同、`unknown` 缺失/失败/不支持；只读，写操作重检，不能将 `unknown` 当作一致）。冲突时读取 `details.thread`、`details.host` 和 `details.remediation`，核对 `permissions`、`approvalPolicy`、`approvalsReviewer` 及两份线程来源，由用户在目标面板选择线程现有权限对应模式（如线程 `:workspace / on-request / user`、宿主 `:danger-full-access / never / user` 时选线程侧 `auto`，不自动升级）；确需采用宿主侧权限须由用户明确决定并在面板操作；两份线程设置不一致或缺失时先核对不猜测；原受管任务仅在已授权、权限符合且可恢复时续接，不借切模式绕过冲突。
- **会话命名（`codex_session_rename`）**：为明确的 `thread_id` 设置 `name`，同时提供准确 `cwd`。服务先核对原生线程与工作目录，经官方 `thread/name/set` 写入并回读一致后返回 `naming=native`。不启动模型轮次、不修改权限；超时先读取原线程名称，不自动重放。源码支持不代表旧版全局服务已加载该工具，先检查工具列表；API 回读不代替 UI 目视检查。
- **任务派单（`codex_task_start`）**：交接文本至少包含目标、允许修改的路径、输入材料、不能触碰的内容、验证命令和完成标准。`plugin` 与 `managed` 均须传入新的 `request_id`、明确的 `mode`、绝对 `cwd` 与 `prompt`；仅 `plugin` 模式另传 `thread_id`（`managed` 模式禁止传 `thread_id`，切勿将 `thread_id` 与必填 `request_id` 混淆）。保存返回的 `task_id`；`queued` 仅表示受理；通信超时后查询原任务或用同一 `request_id` 重试，不另造编号重发。

### 3.3 查询、审批、结果、续接与取消

- **查询与审批**：使用 `codex_task_status` 查询状态、事件游标及待处理请求，下次带 `after_event` 接续读取至 `has_more=false`，间隔随任务时长调整。`waiting_approval` 时：`plugin` 模式由用户在插件 UI 审批；`managed` 模式把 `pending[].approval_url` 作为可点击链接交给用户在本机浏览器选择允许本次、拒绝或取消（无需在 VS Code 打开或接管，不自动弹窗抢焦点；链接仅在原服务和请求存活时有效，不可用时查原任务不重派；调用者不能用 `codex_task_respond` 或自动操作审批页代批）。普通问题回答可通过 `codex_task_respond` 传入待处理编号与预期轮次，答案结构须对应原问题。
- **读取结果**：终态后调用 `codex_task_result`。`content_json` 为可分页 JSON 文本片段，按 `next_cursor` 顺序拼接后解析，检查答复、文件变更、实际命令退出码与未解决事项；不把模型口头声明等同于验证证据。
- **续接与取消**：`codex_task_continue` 需 `task_id`、新 `request_id`、`prompt`、上一轮 `expected_turn_id`，仅上一轮终止后受理并保留旧轮次结果。`codex_task_cancel` 须带 `expected_turn_id`（插件续接处于 `queued` 或 `interrupted_unknown` 且无当前轮次时可显式传 `null`，核对未提交后取消）。收到 `cancelling` 后继续观察，仅后端确认才返回 `cancelled`；取消不能以杀插件进程替代，也不扩大为暂停用户整个会话目标。

### 3.4 失败恢复与健康检查

- **`SESSION_BUSY`**：同会话租约、活动状态或待处理输入不允许新任务；不同会话不因目录重叠互斥。租约冲突返回占用方 `task_id` 且不自动排队；不同 `plugin`／`managed` 会话在同一 `cwd` 并行须事先约定不重叠修改范围。
- **`interrupted_unknown`**：无法确定提交或终止结果时保留租约，按原会话、轮次及提交标识核对，失败后按 1、2、5、10、30 秒退避重试且不重发。插件 owner 暂不可达且已有准确 `turn_id` 时可只读原生历史收回终态（非改派 `managed`）；旧轮次权限证据不在日志末尾时按准确 `turn_id` 流式查找完整日志；仍未知时保存编号和证据，不用删库或超时解锁。`owner_lost` 是 worker 心跳事件；插件不可达单独记录 `plugin_owner_unavailable`。
- **权限与恢复拒绝错误**：`PERMISSIONS_UNAVAILABLE`／`PERMISSIONS_CONFLICT`／`PERMISSIONS_CHANGED` 先核对宿主选择及用户数据目录，不改派 `managed` 绕过；`PERMISSIONS_MISMATCH` 查看原任务终态、命令结果及权限事件，不直接重派（修复版本可通过 `permission_inheritance=host-selection-native-turn-context-v1` 识别，但不代替实测）。`THREAD_RESUME_REJECTED` 表示后端明确拒绝 `thread/resume` 且未提交新轮次（`reason=unclassified_backend_rejection` 不证明插件持有）；仅后端明确报告插件持有时返回 `THREAD_OWNED_BY_PLUGIN`，由用户释放面板持有后续接原受管任务或在已授权且权限一致时走插件路径，不自动接管、关闭或重放。诊断字段仅含 `method`、数字 `backend_error_code`、`backend_message_sha256`，不回传原始后端错误正文。
- **worker 健康与排队中断恢复**：0.2.1 起 `capabilities.worker_health` 返回调度与恢复循环健康状态、进度年龄及重启次数；`worker_loop_failed` 在 stderr 记录异常类型和栈位置；健康依赖两条循环进度，SQLite 锁异常退避重试，事件循环超时未推进停止续约。排队中断的插件续接核对本次命令、上一轮编号、owner 快照及原生线程完整历史：轮次序列一致、会话空闲、无本次输入及写入证据时恢复返回 `failed / CONTINUE_NOT_SUBMITTED`、空轮次取消返回 `cancelled`（命令与租约同事务结清）；存在新轮次时每轮须已终止且含唯一完整无调度前缀输入；否则保留原有保护。
- **CLI 派单**：需 `--wait` 保持拥有后端连接的进程存活，参数使用 JSON 文件：

```powershell
python scripts/launch.py --call codex_task_start --arguments task.json --wait
python scripts/launch.py --call codex_task_status --arguments status.json
```

## 4. 规范

完整权限适配、参数幂等、工作区并发与协议维护约束见[公共规则](00.common.rules.md)。派单前确认目标会话权限一致且空闲，绝不通过任务参数覆盖安全策略、绝不代批权限、绝不删库解锁。

## 5. 验收

1. **静态与协议验证**：技能结构检查（含隔离目录）、Markdown 检查、运行时虚拟环境自包含单测（`-m unittest discover -s scripts -p "test_*.py"`）及安装文件全量 SHA-256 哈希比对通过。标准 MCP 客户端初始化、列出八项工具、调用只读查询；非法字段、超限提示词和错误编号返回结构化错误。会话命名验证准确 `thread_id` 与 `cwd`、原生回读、错误工作目录不写入及超时不重放；源码检查、真实接口调用、全局安装加载和 UI 展示分别记录。
2. **行为、并发与健康回归**：在用户指定验收会话完成提交、查询、验证产物、读取结果、续接、取消闭环，核对重复请求不增轮次、重启匹配同轮次、断开/失败/审批等待/非法响应/三种模式目录并发与同线程冲突证据。受管审批验证本机链接、原连接回复、多个 pending、重复点击、取消和服务端失效、跨源拒绝、MCP 不能代批（协议模拟、真实 App Server、用户点击三者分别记录）。运行 `python -m unittest discover -s scripts/verdantflare_agent_codex/tests -p "test_*.py"`（独立临时库，真实案例只读原生历史），覆盖二十批每批八连接原子受理、目录联接、NULL 线程绑定、取消隔离、提交回执丢失、终态落库失败、worker 心跳与插件 owner 分离、重复恢复、超 8 MiB 日志尾部权限查找、只读历史分页回收、隔离安装/回滚与运行摘要冻结，以及 worker 健康回归（SQLite 异常、意外返回/取消、事件循环阻塞、单次认领、停止心跳、精确撤销未认领提交）。
3. **业务与权限完成判定**：约定产物存在、内容正确、命令退出码为 0 且无未解决事项；插件模式验收不被独立后端测试替代；技能可见、MCP 已注册、真实工具可调用和人工确认分别报告；跨智能体接入须至少另一宿主在新会话实测。权限修复验收检查首次派单、续接、`managed` 转 `plugin`、权限收紧、来源不明与原失败命令，以准确原生 `turn_context`、退出码及服务终态举证；真实审批负向用例只观察等待并取消或超时，不代批。
4. **交付记录**：包含服务与插件版本、模式、任务与轮次编号、产物位置、实际验证结果、未完成项及人工结论；公开报告脱敏账号、认证信息和本机路径。
