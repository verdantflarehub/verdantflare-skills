# 执行流程

## 1. 接入检查

确认服务已安装，宿主 MCP 列表包含 `verdantflare-agent-codex`。配置入口由 `VERDANTFLARE_AGENT_CODEX_SERVICE` 指定，默认从用户数据目录的 `verdantflare-agent-codex/service.json` 读取。Python 启动器只读取配置并调用安装好的服务，不在调用时下载依赖。

运行 `codex_capabilities`，必要时传入 `cwd` 与分页 `cursor`；选择用户指定的会话编号。找不到在线持有者时让用户打开该会话，不自行改派其他用户会话。

## 2. 任务交接与派单

从当前 VS Code Codex 会话派兄弟任务时，使用宿主原生协作创建和续派。获取兄弟线程的原生 Session ID 后，使用 `scripts/open_panel.py <当前项目目录> --session <Session ID>` 在同一个窗口打开它。入口沿当前 Codex App Server 的进程树定位扩展宿主，由配套扩展核对项目和会话标签。返回的 `opened=true` 证明标签已打开，任务状态和回复仍从原生协作通道读取。该入口适用于已安装配套扩展的 Windows VS Code 桌面窗口。

对使用本地套接字的 Windows 项目窗口，先用 .NET 8 SDK 构建 `resources/panel-transport/PanelTransport.csproj`。安装器的 `--panel-transport` 接收一个 JSON 文件，其中 `client` 指向构建的 PanelTransport.exe，`hosts` 数组的每项填写项目绝对路径 `cwd` 和当前用户私有目录内的套接字绝对路径 `socket`。构建产物需连同旁边的运行文件保留在稳定位置。

使用安装后技能中的 `scripts/open_panel.py <项目目录> --code <Code.exe路径>` 打开窗口。非默认安装位置加 `--config <运行目录/config.json>`。该入口按项目使用独立 VS Code 配置目录，同时加载本机 Codex 扩展及配套窗口扩展。首次打开后，在插件中选择所需权限，再用 `codex_session_create` 取得面板 Session ID，通过 `codex_capabilities` 核对其归属和权限。关闭该窗口即可结束本次宿主连接。

需在面板查看并通过插件派单的专用会话，创建时须与宿主显式权限选择一致。managed 创建使用自身配置，任务参数不能指定或覆盖权限；不能保证一致时，创建后只走原受管路径，不在面板接管。已授权且权限一致时，才可通过 VS Code 的 `vscode://openai.chatgpt/local/<thread_id>` 路由打开并查询持有者；该路由依赖宿主版本，不等于 MCP start 支持新建插件标签，不保证其他 App Server 能恢复。不得自动选择无关用户会话。

派单前查看 `threads[].permission_alignment`：`match` 表示读到的双方完整字段一致，`conflict` 表示至少一项不同，`unknown` 表示字段缺失、读取失败或不支持。该字段只读，写操作仍重新检查，不能将 unknown 当作一致。

冲突时读取错误的 `details.thread`、`details.host` 和 `details.remediation`，核对 `permissions`、`approvalPolicy`、`approvalsReviewer` 及两份线程来源。由用户在目标面板选择线程现有权限对应模式，再查询一致性。例如线程为 `:workspace / on-request / user`、宿主为 `:danger-full-access / never / user`，应让用户选择线程侧的 `auto`（工作区权限），而不是自动把线程升级为完全访问。确需采用宿主侧权限，须由用户明确决定并在面板操作。两份线程设置不一致或缺失时先核对，不猜测选择。原受管任务仅可在已授权、权限仍符合要求且可恢复时续接，不能借切换模式绕过冲突。

使用 `codex_session_rename` 为明确的 thread_id 设置 name，同时提供准确 cwd。服务先核对原生线程与工作目录，经官方 `thread/name/set` 写入并回读一致后返回 naming=native。此操作不启动模型轮次，不修改权限；超时先读取原线程名称，不自动重放。源码支持不代表旧版全局服务已加载该工具，先检查工具列表。API 回读不代替 UI 目视检查。

交接文本至少包含目标、允许修改的路径、输入材料、不能触碰的内容、验证命令和完成标准。调用 `codex_task_start`，`plugin` 与 `managed` 两种模式均必须传入新的 `request_id`、明确的 `mode`、绝对 `cwd` 与 `prompt`；仅 `plugin` 模式另传 `thread_id`（`managed` 模式禁止传 `thread_id`，切勿将 `thread_id` 与必填的 `request_id` 混淆）。

保存返回的 `task_id`。启动返回 `queued` 仅表示任务已受理，不是执行成功。通信超时后查询原任务或使用同一请求编号重试，不另造编号重发。

## 3. 查询、输入与结果

使用 `codex_task_status` 查询状态、事件游标及待处理请求；下次带 `after_event` 接续读取，直到 `has_more=false`。间隔随任务时长调整，不紧密循环刷请求。

`waiting_approval`：plugin 模式由用户在插件 UI 审批；managed 模式把 `pending[].approval_url` 作为可点击链接交给用户，在同一台机器的浏览器中查看完整请求并选择允许本次、拒绝或取消。无需在 VS Code 打开或接管受管会话，不自动弹窗抢占焦点。链接仅在原服务和对应请求存活时有效；不可用时查询原任务，不重派。调用者不能用 `codex_task_respond` 或自动操作审批页自行批准权限。普通问题的回答可通过 `codex_task_respond` 传入待处理编号与预期轮次，答案结构必须对应原问题。

终态后调用 `codex_task_result`。结果的 `content_json` 是可分页的 JSON 文本片段，按 `next_cursor` 顺序拼接后再解析，检查答复、文件变更、实际命令退出码与未解决事项。不要把模型口头声明等同于验证证据。

## 4. 续接与取消

`codex_task_continue` 需要 `task_id`、新的 `request_id`、`prompt`、上一轮 `expected_turn_id`。仅上一轮终止后受理；同一任务保留旧轮次结果。

`codex_task_cancel` 须携带 expected_turn_id。插件续接处于 queued 或 interrupted_unknown 且没有当前轮次时，可显式传 null，按第 5 节核对未提交后取消。收到 `cancelling` 后继续观察，只有后端确认才会返回 `cancelled`。取消不能以杀死插件进程替代，也不能扩大为暂停用户整个会话目标。

## 5. 失败恢复

`SESSION_BUSY` 表示同会话租约、会话活动状态或待处理输入不允许新任务；不同会话不会仅因目录重叠互斥。租约冲突返回占用方 task_id，可查询该任务；不会自动排队。不同 plugin／managed 会话在同一 cwd 可直接并行，必须事先约定不重叠的修改范围。

`interrupted_unknown` 表示无法确定提交或终止结果，仍保留租约。服务会按原会话、轮次及提交标识核对；恢复失败后按 1、2、5、10、30 秒退避重试，恢复不会重发任务。插件 owner 暂不可达且已有准确 turn_id 时，可只读原生历史收回终态；该操作不是改派 managed。旧轮次权限证据不在日志末尾时，按准确 turn_id 流式查找完整日志。仍未知时保存编号和证据，不用删除数据库或超时解锁。owner_lost 是 worker 心跳事件；插件不可达单独记录 plugin_owner_unavailable。

`PERMISSIONS_UNAVAILABLE`／`PERMISSIONS_CONFLICT`／`PERMISSIONS_CHANGED` 表示权限来源无法确认、冲突或在提交前变化；先核对宿主选择及用户数据目录，不改派 managed 绕过问题。`PERMISSIONS_MISMATCH` 表示原生轮次生效权限与已记录选择不符；查看原任务终态、命令结果及权限事件，不能直接重复派单。修复版本可通过 capabilities 的 `permission_inheritance=host-selection-native-turn-context-v1` 识别，但该标记不代替实际轮次验收。

`THREAD_RESUME_REJECTED` 表示后端明确拒绝 `thread/resume`，未提交新轮次；`reason=unclassified_backend_rejection` 不证明插件持有。仅后端明确报告插件持有时返回 `THREAD_OWNED_BY_PLUGIN`，由用户释放面板持有后续接原受管任务，或在已授权且权限一致时走插件路径；不得自动接管、关闭会话或重放。诊断字段提供 `method`、数字 `backend_error_code`、`backend_message_sha256`；为避免泄漏提示词、路径和凭据，不回传原始后端错误正文。历史版本已丢弃的错误无法据此追溯原因。

CLI 派单需要 `--wait` 让拥有后端连接的进程保持存活；MCP 客户端保持连接时可异步查询。完整参数使用 JSON 文件：

```powershell
python scripts/launch.py --call codex_task_start --arguments task.json --wait
python scripts/launch.py --call codex_task_status --arguments status.json
```

0.2.1 起 capabilities.worker_health 返回调度与恢复循环的健康状态、进度年龄及重启次数。worker_loop_failed 会在 stderr 记录异常类型和栈位置；健康依赖两条循环进度，不能仅凭进程存在或独立心跳线程判断可派单。SQLite 锁异常退避重试；事件循环超过健康窗口未推进时停止续约。

排队中断的插件续接须核对本次命令、上一轮编号、owner 的当前快照及原生线程完整历史。双方从上一轮起的轮次序列一致、会话空闲、未发现本次输入且没有开始写入的证据时，恢复返回 failed / CONTINUE_NOT_SUBMITTED，空轮次取消返回 cancelled。命令与租约在同一事务中结清。若上一轮后存在新轮次，每轮须已终止且原生记录包含唯一、完整、无调度前缀的文本输入。记录不完整、可能来自调度服务、owner 更换、已记录提交或并发认领时保留原有保护。

安装前先执行 `python scripts/generate_build.py` 生成确定性运行清单；核对维护源、安装副本与实际连接进程的 service_build。清单 verified=false 或旧进程缺少标识时，不报告新版本已加载。版本切换等待在途任务安全窗口，不混跑新旧租约语义。

## 6. 可选会话列表筛选

插件维护任务先执行只读探测，再按已有任务授权显式应用补丁；状态、升级和回滚命令见[工作区会话补丁](workspace-sessions.md)。普通安装不自动启用。验证时分别记录脚本测试、磁盘应用、实际加载和双项目 UI 体验，不为加载补丁中断活动任务。
