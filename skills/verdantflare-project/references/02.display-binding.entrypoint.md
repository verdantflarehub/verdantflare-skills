# 素材展示关联与专用片场审阅（02.display-binding）

## 1. 输入与输出

- **输入**：已绑定项目的最新固定修订（`project.open` 产物）、唯一领域文档 `project-content`、Artifact 版本元数据映射（`versions`）及待排查的展示问题或专用片场审阅目标版本。
- **输出**：经映射核对与回读验证的业务展示关联修订、`scripts/check_video_display.py` 只读关联检查结论、实际字节解码核验记录，以及区分已有认可与当前审阅状态的交付报告。
- **公共依据**：[MCP 授权与工作副本规范](./00.common.rules.md)。

## 2. 分类

按排查对象与核验层级分为两类：

- **页面展示关联排查与修复**：针对“只有名称、内容不显示、位置不对”或视频阶段交付，按项目实际 `category`（如 `video`）核对文件归档层、领域引用层、页面消费层与真实 MIME 播放器兼容层。
- **专用片场审阅核对（`project.review_open` / `world.review_open`）**：固定具体目标版本，区分 `availability`、`missing`/`requirements`、`coverage` 与人工记录，衔接既有用户认可与新增复用范围缺口。

## 3. 工作流

### 3.1 故障分层定位与映射规划

1. 打开原项目最新修订，读取 `domain_documents` 中唯一 `project-content`，核对实际 `category` 与服务支持的 Schema（现有 `video` 项目不因技能适用于短剧而自动迁为 `ai_short_drama` 或 `creative_video`）。
2. 分别查明四层状态：文件是否已归档、领域对象是否引用、字段是否被当前页面消费、真实 MIME 是否支持该播放器。
3. 备份固定基线，建立“目标 → 字段 → `file_id` → `ContentRef` → 实际 MIME”映射表；若需抽帧作为派生封面，保存来源视频摘要与时间点，不重新生成视频；依赖服务器分配新 `file_id` 时，先归档派生文件（中间状态仅报告已归档），再基于返回修订提交完整业务关联。

### 3.2 提交回读与只读脚本校验

1. 提交关联修订前检查不丢失历史、不改变无关选用；提交后回读固定修订与领域 JSON。
2. 依据 Artifact 返回的 `metadata` 核对 MIME 与摘要，并按本次变更范围受控下载实际字节解码（覆盖缩略图、角色图片、主交付媒体与修正后的媒体类型；已核验的不可变版本可复用，无需重复全量下载）。
3. 运行只读关联校验器核对结构与 MIME 映射：

```text
python -X utf8 scripts/check_video_display.py --manifest open.json --content project-content.json --versions metadata.json
```

仅本轮交付确需成片或完整卡片时添加 `--require-output`、`--require-covers`；用 `--expect-unit`、`--expect-cast` 核对明确对象清单。

### 3.3 专用片场审阅查询与缺口补齐

1. 调用 `project.review_open` 或 `world.review_open` 前先固定具体目标版本，不用旧候选状态解释当前资产。
2. 分别读取返回中的 `availability`、`missing`/`requirements`、`coverage` 与人工记录：判断是内容/权限不可读、证据职责未映射/无验证器，还是确实缺少该范围材料。
3. 仅在当前交付确需更大复用范围时补齐缺口：先核验已有工程、图片与来源的固定引用，复用已验证字节不重复上传，按实际契约与新业务修订修正映射并保留已发布版本。

## 4. 规范

- **现有 `video` 分类展示槽位契约**：
  - 项目封面用 `cover_file_id`；可播放当前交付候选用 `video.output_file_id` 并注明真实候选状态（候选可预览与正式选用分开，不因尚未终审故意不绑定已交付的候选预览；该展示引用不等于 `manifest.selections`、人工终审或 World 发布）。
  - 每个已产出故事板的 `image_file_id` 绑定同一镜头真实图片/抽帧；`reference_file_ids` 只放参考图、`result_file_ids` 只放对应结果视频；配音、方案、记录及其他文件归 `file_ids`（禁止把 WAV/JSON/MP4 放进参考图，禁止把 PNG 放进视频结果）。
  - 故事板当前结果与用户明确使用的制作版/剪辑来源一致，依摘要与固定引用核对；保留旧候选并标明历史，未经批准的新版不因编号较大自动取代现用版；页面卡片顺序按当前叙事，回顾复用镜头不冒充新案例。
  - `video.cast` 使用真实角色条目与单人身份图，已有同项目图片可绑定 `portrait_file_id`，不编造来源角色项目，多人拼图不得作为每人头像。
  - 总体配乐、完整旁白与制作文档使用该分类已有文件预览入口并记录查看位置；若有专属页需求而当前 Schema/前端不支持，按设计或实现缺口记录，不制造“配乐故事板”或未知字段。
- **字段与证据边界**：只有名称和 overview 中的本地路径不能代替媒体引用；Manifest 有文件不等于对应页面有内容，前端不支持的槽位不能塞入错误字段；`versions` 必须来自 Artifact 实际 version 元数据，严禁用扩展名猜 MIME；`check_video_display.py` 不执行上传、不创建批准，也不替代当前 Schema、权限、字节解码或浏览器渲染验证。
- **审阅状态与已有认可红线**：`mapping_state=mapped` 仅表示目标可定位，不保证机位、工程恢复和完整片场均已验证；普通 `reference/doc` 附件不能按文件名猜成工程或相机证据。既有用户认可按固定版本、原话与用途继续沿用（如“空间白模+外观参考”不等于 `full_set`）；专用审阅的 `unreviewed` 不撤销既有认可，不自动构成重验或重生成理由，也不能把旧认可导入为新目标的完整人工批准。服务返回 agent 仅可 `comment` 时，禁止通过通用 commit、自造记录或请求头写成 `approve`；不为使审阅状态变绿而自动登记新 World 版本、切换选用或扩张资产用途。

## 5. 验收

- `check_video_display.py` 按本轮交付范围执行通过（0 errors），且所有变更媒体的 Artifact `metadata` MIME/摘要与受控下载解码验证均已完成。
- 严格区分两类证据：MCP 核验提供关联、类型与内容可读证据，不声称看到了真实页面；明确的前端修复或页面验收任务另按宿主规范完成真实页面检查，普通项目同步无需额外浏览器操作。
- 交付报告明确呈现绑定位置、候选状态、既有认可延续范围及仍存在的 Schema/前端或审阅缺口。
