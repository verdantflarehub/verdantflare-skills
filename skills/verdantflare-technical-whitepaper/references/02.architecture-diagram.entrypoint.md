# 总体架构图与部署架构图设计绘制（02.architecture-diagram）

## 1. 输入与输出

- **输入**：系统主体清单、功能模块、协议与数据流向、物理承载与集群边界、既有图源及人工审核反馈。
- **输出**：可编辑图源（如 SVG、绘图源或 Mermaid）及实际渲染导出的总体架构图或部署架构图（含内置功能性图例，不含整图标题、简介与审核状态）。
- **公共依据**：[技能入口](../SKILL.md)；文档侧图题与审核状态编排见 [01.whitepaper.entrypoint.md](./01.whitepaper.entrypoint.md)。用户于 2026-11-16 最终明确：总体架构图不渲染图名简介和审核状态；图例属于图的一部分，采用图块加解释，新建、首期、利旧由图例解释。本能力将该要求作为默认规范，用户后续明确要求可调整。

## 2. 分类

按架构图回答的核心问题分为两类，职责严格分离：

| 图类型     | 核心职责简述                                       |
| :--------- | :------------------------------------------------- |
| 总体架构图 | 呈现使用者、业务主体、功能、协议与输入输出流向     |
| 部署架构图 | 呈现服务物理承载、服务器或集群边界、容器与存储连接 |

- **总体架构图**：功能层次按实际设计表达，不以同机部署推导业务隶属关系；区分系统负责运营的外部对象、成果接收端和支撑依赖；具体摆放依用户指定或关系可读性决定。
- **部署架构图**：业务独立与物理共址可同时成立，保持与总体图的主体对应，不把业务依赖自动画成同一服务器内的组件；沿用图文分离原则，除非用户对该图明确另有要求。

## 3. 工作流

1. **恢复上下文与清单梳理**：读取当前需求与有效设计，恢复已有图源及人工反馈，区分有效决定与历史草稿；列出主体、功能、关系及证据，确定绘制总体图还是部署图。用户明确暂停绘图时停止该制作任务。
2. **结构优先与视觉编码**：先确定节点与连线结构，再定义业务色系、建设状态和阶段样式。已有结构足以表达架构时先出可审阅图，不为不影响结构的字段细节反复拖延出图。
3. **图内图例编排与导出**：将图名简介、状态说明留在文档，将图例编排进架构图独立区域，与主图节点留出清晰间隔、不覆盖连线。图例图块与主图使用同一套样式定义，在可编辑图源中作为图的一组元素维护。导出可查看的图片（PNG/SVG 等）并保留可编辑源，不覆盖需保留的批准原件。
4. **视觉渲染核验与返修**：实际查看最终导出文件（只生成源文件不算视觉检查），逐项检查架构语义、文字边界、图例与节点样式一致性。视觉不合格时修改原图源再导出，不以新增另一张临时图充当原审阅入口；修改后只重验受影响内容。

## 4. 规范

### 4.1 架构图内保留与禁止元素

- **必须保留**：架构所需的主体名称、模块名称、功能、协议、关系、连线，以及解释视觉样式的图例。通用参与者使用“用户”，不把项目负责人的昵称写入角色节点，除非用户明确要求展示具体身份。
- **严禁出现**：整图标题、图名、介绍、摘要或说明性页脚；“已通过”“待审核”“CP0 未通过”等审批或进度状态。模块名称不是整图标题，协议标签不是简介，不得为清理装饰文字而删除必要架构信息。
- **禁止节点状态贴纸**：节点不附加“新建”“利旧”“首期”“后续”等解释性标签，也不得把这些词换成角标、徽章或水印继续贴在业务节点上；一律用有确定含义的视觉样式表达并在图内图例解释。

### 4.2 图内图例（图块加解释）与配色语义

- **图例归属与构成**：图例属于架构图的一部分，须随 PNG、SVG 或其他导出文件完整输出，置于图内独立区域且不覆盖连线。审核状态单列在文档状态区域，不属于图例。每个图例项由一个可见示意图块及紧邻的简短解释组成，图块复现图中实际填色、边框或连线样式；不只列颜色名称，不在图块中塞长说明。
- **最小必要原则**：只保留有解释必要的功能性样式。主体名称已在节点中明确，不再添加“个人助理”“VF Center”“VF Station”等描述性图例；普通数据线和箭头含义直观，不另加数据流方向、双向交互图例，确有非标准连线语义时才解释其特殊含义。
- **默认功能性图例集合**：保留利旧能力、新建能力、首期接入、后续扩展；标签省去“平台”等可从上下文判断的前缀，不扩充无关图例，不为不存在的类别添图例。
- **正交视觉编码（防语义冲突）**：业务归属和建设状态分开编码——不同主体用不同色系；同一主体色系中饱满色表示利旧，浅色表示新建；利旧需改造时另用边框等样式并提供对应图例；没有事实依据的复用不能画为已有能力。实施阶段另用独立样式（如实线框表示首期、虚线框表示后续，同一套图中保持一致），不得同时用浅色表示新建和后续，以免无法区分“首期新建”与“后续新建”。组合图例应能解释实际出现的组合。

## 5. 验收

### 5.1 可观察检查清单

- 总体图与部署图职责分明；同机服务仍有独立业务边界。
- 架构图片中整图标题、简介、审核状态的数量均为零；图例随图片完整导出。
- 节点内不残留新建、利旧、首期等状态文字或同义徽章；业务模块名称及必要协议仍完整。
- 图内图例项均为实际示意图块加解释，仅解释必要的功能性样式，不重复主体名称，不解释普通数据线，无冗余前缀，建设状态与阶段语义不冲突。
- 实际查看最终渲染图像，文字不裁切、节点不重叠、箭头不误指，导出图片与可编辑图源一一对应。

### 5.2 规则辨识样例

- **不合格**：图片顶部写“总体架构图”，右上写“CP0 未通过”，即使主体结构正确也不合格；图内独立图例本身是正确组成，不是违规项。
- **不合格**：节点写“服务 A〔新建·首期〕”，或把这段文字改成角标，仍属将图例解释混入业务节点。
- **合格结构**：文档标题为总体架构图；图片画用户、业务主体、模块及协议箭头，并在图内独立图例区域用饱满色图块说明利旧、浅色图块说明新建，再以实线和虚线图块说明首期与后续。

本节样例用于规则辨识，不证明任何既有图片已修正或获得人工认可。静态检查只验证技能结构；实际图稿必须另做视觉核验。
