# 技能研发检查

用户要求优化 `verdantflare-music` 时，以跨项目的制作体验和可验证能力为目标；歌曲项目只作为回归案例，不因为个案反馈强制所有歌曲采用同一曲风、版本数或审核流程。

## 能力分层

| 层级 | 核对什么 | 不能推断什么 |
| --- | --- | --- |
| 技能 | 入口路由、审核与返工规则 | 写了步骤不等于工具已实现 |
| 本地服务 | API 签名、模型、测试与产物契约 | 源码存在不等于镜像已发布 |
| 当前部署 | 镜像版本、实际 MCP 工具清单、已配置后端 | 连接可用不等于每个新参数都可用 |
| 音质 | 真实素材的分轨、等响度 A/B 与人工听审 | 单测、哈希和格式合格不等于好听 |

先找出用户体验中的具体断点，再改对应层；只改技能文本不能修复服务丢轨，只改服务源码不能让旧部署获得新能力。若改动跨层，分别更新技能参考、服务契约/测试和简明用户指引；研究资料留在设计文档，不塞进使用指引。

配置示例只记录变量名和非密钥地址。`.env` 不会自动把 Music MCP 注册到宿主；只有可信宿主已注册工具并安全注入令牌时才按实际工具清单执行。不得把 `.env` 中令牌复制到 `config.toml`、命令行、日志或聊天，也不得为测试连接绕过凭据审查。部署和发布须单独核对授权及目标清单，不因本地代码完成而自动推进。

交付前运行技能校验、引用链接与相关代码契约测试；涉及音质承诺时还需真实音频对照。缺少依赖、独立分轨或远端工具时保留未验证状态，明确下一项可执行的验证，不制造“已修好”的听感结论。
