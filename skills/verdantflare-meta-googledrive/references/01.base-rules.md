## 2. 软连接与目录结构契约

项目 `.gdrive` 必须是指向 `<drive-root>/<项目命名空间>/` 的目录软连接（Windows 符号链接或 `junction`），写入即落在 Google Drive 映射盘，由桌面客户端负责上传与跨机同步。唯一自动维护边界是其中的 `managed/`；`managed` 名称固定，不接受参数改成其他目录。

```text
<project>/.gdrive  →  <drive-root>/github.com/<group>/<project>/
├── managed/                # 助手唯一维护区，全部同步
│   ├── approved/
│   ├── pending/
│   ├── references/
│   ├── receipts/           # 入库原因与审核参数
│   └── config.json         # 仅 schema 与命名空间，不含本机路径
├── 品牌素材/                # 人类管理，示例；助手不创建
└── 客户提供/                # 人类管理，示例；助手不创建
```

## 3. 核心硬约束

### 3.1 零冗余与无历史存储边界

- `.gdrive` 内只存放需要同步的受管素材、`receipts/` 回执与 `config.json`，不设 `history/` 或任何仅本地目录。
- 被替代且无任何 Markdown 引用的旧版直接通过 `remove --apply` 移除；临时、可抛弃或需要暂留的文件只放项目 `.tmp/`。
- 相同逻辑素材更新时生成新的内容 SHA-256 版本名 `<logical-name>--<sha256>.<ext>`，严禁在原内容摘要路径直接覆盖修改文件。

### 3.2 人工目录只读保护

- `.gdrive` 下 `managed/` 以外的目录均由人类管理，助手严禁自动创建、重命名、搬迁、覆盖、删除或收编。
- 允许只读检查人工目录的引用，已位于人工目录的素材满足入库位置要求。
- 用户明确指定外部文件为输入时，可复制入 `managed/` 并保留原文件；对外部或人工目录的修改必须有针对该目录的明确指令。

### 3.3 引用保护与 Git 职责边界

- 已被 Git 跟踪的文件（以 `git ls-files` 为准）不属于本技能职责；被 `.gitignore` 排除或未跟踪的本地文件，只要被任意 Markdown 引用（或经用户显式指定跨机复用），必须入库 `.gdrive/managed/` 并改写为文档相对路径。
- 仍被任何 Markdown（含归档文档、技能文档及 `.tmp` 内文档）引用的版本严禁移除，即使不再是最新版本；代码围栏中的示例链接不算实际引用。
- Google Drive 是大型素材跨机存储的唯一约定；旧有 OneDrive 素材按引用逐项入库，不整盘迁移。
- 项目研发源码及本技能唯一维护源进入 Git，安装副本不单独修改；`.gdrive` 软连接、大文件与机器状态不进 Git，`init` 自动在 `.gitignore` 中加入 `/.gdrive`。

### 3.4 命名空间、多机兼容与审核证据

- 远端默认路径结构为 `我的云端硬盘/github.com/<group>/<project>/`（不含 `.gdrive` 与 `.tmp`），共享盘也可作为显式根目录；分支名和电脑名不作为项目根，多人共享时命名空间必须完全一致。
- 命名空间与 Git 托管地址分离：只有 `origin` 明确对应预期项目时才推导，严禁拿 GitLab `origin` 冒充 GitHub。
- 各机器的挂载路径由各自的软连接目标决定，共享的 `config.json` 仅记录 `{"schema": 3, "namespace": "..."}`，不含本机路径，多台电脑互不覆盖。
- `approved/` 分桶必须传入真实审核人 `--reviewer` 与审核证据 `--evidence`；`receipts/` 随素材同步保存入库原因和审核参数，审核原始证据仍在项目 Git 文档中维护。
