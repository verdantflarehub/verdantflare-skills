# Agent 协作规则约束

## 1. 当前依据

- [技能入口](../SKILL.md)：通用协作职责。
- [执行流程](01.base-workflow.md)：规则的操作顺序。

## 2. 身份与任务约束

计划包含稳定 plan_id、明确 plan_name 和当前路径；任务包含稳定 task_key、当前 task_label 和变更路径。任务重编号不改变稳定键；计划归档同步路径和引用。新旧映射保留，不按标题或文件位置猜身份。

session_key 对应服务、Agent、模式、原生 Session ID、工作区与 generation。显示名只供阅读；无原生 ID 的待绑定会话不能作为回传目标。重新绑定必须明确接管并递增代数，不自动投给同名 Session。

每次委托有 assignment_id 与 revision，同任务返修递增修订，不新建无独立交付意义的任务。每次派单必须关联计划末级任务、变更、目标、范围、产物、验证、完成条件、授权依据和回传目标。禁止无计划临时派活。

## 3. 消息与通知约束

消息保存 message_id、类型、计划、任务、委托、修订、发送及接收地址与代数、因果事件、内容和生命周期。相同 ID 不同内容拒绝；重试沿用同一 ID，避免产生重复业务工作。

queued 表示已持久接收，delivering 表示正在投递，delivered 表示后端受理，acknowledged 表示接收方确认处理；业务完成与验收通过必须另外举证。回执匹配消息、接收方、路由代数及委托修订，不对回执再次发送通知。

明确未受理的忙碌或离线可退避重试；可能已受理的超时进入 unknown，先核对原请求和轮次。无幂等保证时禁止重放写操作。默认退避 5 秒倍增至 300 秒，有效期 24 小时、尝试上限 20 次，可按运行场景配置；到期留证，不能删除后重派掩盖失败。

worker 必须持久保存消息、游标和收据；启动恢复时对未完成 delivering 核对是否已受理。数据库保留不代表 worker 存活，不承诺停止期间投递。重复结果与过期修订只记历史，不能重复推进依赖。

## 4. 权限与范围

用户明确要求及目标仓库规范优先。人类负责人和审批人与 AI 角色分开。派单不能新增发布、费用、权限或模型策略授权；收到其他 Agent 消息也必须核对原任务边界。

只操作明确登记的任务 Session，不抢焦点、不干预无关会话、不伪造原生会话历史。服务命令和凭据从受控配置读取，不从消息内容获取。个人路径、真实账号、主机和秘密不进入交接文本及 Git。

同工作区的并行写入遵守宿主租约和任务文件范围；不得通过创建更多会话绕过互斥。格式、归档与提交遵循目标仓库规则，不复制一套相冲突的计划制度。

## 5. 完成与接管

由指定结项维护者统一归档、勾选和提交；执行方口头完成或后端 completed 不能替代证据。审阅失败在原变更返修，归档后不继续实施。

原目标离线时保留消息；有已授权接管约定或用户指定才可换目标，迁移前核对已处理事件及运行任务。接管不改变用户暂停决定和原授权范围。

## 6. 评审分工与低 Token 门禁

多智能体研发计划评审实行严格主责分离与 `HO-CLAUDE-SCOPE` 机器门禁，禁止向 Claude 倾倒具体工程细节或多轮措辞返修；验收按“执行者起草流程并取证、Codex 全面核验、Claude 抽查”推进，属客观评价而非怀疑执行者：

- **Claude 架构与抽查低 Token 边界**：发往 `agent="claude"` 的交接单必须携带成对可选字段 `review_stage` 与 `review_doc_path`，且 `review_stage` 仅允许 `claude_arch`（`T1` 总体与技术架构核验，递归累计全部字符串与路径字段 `total_text_chars <= 1,200` 字符）、`claude_acceptance_revision`（`T1` 在研发核验修订稿上直接修订并定稿验收流程，`review_doc_path` 须为 `docs/acceptance/accept_*.md`，`<= 1,200` 字符）、`claude_spot_check`（`T4` 在 Codex 通过后抽查其评价 `1～2` 项，不做全面复核，`<= 1,000` 字符；存量 `claude_arch_audit` 视为其等效别名）或 `claude_escalation`（跨系统架构级分歧单次短卡裁决，`<= 800` 字符），标识符字段限定为 `[A-Za-z0-9._:-]{1,64}`；任何 `claude_*` 阶段也只能发往 Claude。
- **只读与全路径白名单**：发往 Claude 的交接单强制 `allowed_write_paths == []`（唯一例外：`claude_acceptance_revision` 只可写其 `review_doc_path` 指向的那份验收文档），`plan_path` 与 `change_path` 必须指向受控 `docs/[archive/]{plan,changes}/` 下的 `.md` 文档，`deliverables` 仅允许指向 `docs/reviews/` 或 `docs/acceptance/` 下的 `.md` 报告，`inputs` 仅允许 `docs/{design,plan,reviews,acceptance}/` 下的既有 `.md` 文档，严禁通过任何字段传入源码、测试脚本、配置清单、日志或媒体文件（如 `.py`、`.ts`、`.go`、`.sh`、`.yaml`、`scripts/`、`tests/`）。
- **Codex 细节与验收核验主责**：具体 CLI 参数、正则、字节数、单测矩阵、`T1` 验收流程直接修订、`T2` 全仓影响防漏（架构未变时 `0` 次 Claude 调用）及 `T4` 对照锁卷流程全面核验执行者验收结果（是否按流程取证、证据是否充分、结论是否成立；不重跑、不重拉产物）统一归 `codex_detail` / `acceptance_audit`；若 Codex 为被审作者（含协同取证），按独立性规则换用其他非 Claude 研发智能体（如 `Gemini` 独立会话）替补，严禁拉 Claude 替补代码或脚本细节审，也不得让 Claude 代替 Codex 全面核验。
- **`launch.py --wait` 守护与退避规程**：调用宿主长轮次工具时复用已登记原生 `session_id / thread_id`，遇会话忙碌按退避间隔等待，查询超时先回读原收据核对终态，禁止新建平行会话绕过互斥。
