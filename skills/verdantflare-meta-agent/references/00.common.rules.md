## 2. 计划绑定与身份稳定键

计划包含稳定 `plan_id`、明确 `plan_name` 和当前路径；任务包含稳定 `task_key`、当前 `task_label` 和变更路径。任务重编号不改变稳定键；计划归档同步路径和引用。新旧映射保留，不按标题或文件位置猜身份。

`session_key` 对应服务、Agent、模式、原生 Session ID、工作区与 `generation`。显示名只供阅读；无原生 ID 的待绑定会话不能作为回传目标。名称区分原生标题与逻辑名称，回读成功才能声称原生标题已修改；地址必须包含服务、模式和原生 Session ID，受管会话、插件会话和面板会话分别确认，不能自动切换。重新绑定必须明确接管并递增代数，不自动投给同名 Session。

每次委托有 `assignment_id` 与 `revision`，同任务返修递增修订，不新建无独立交付意义的任务。每次派单必须关联计划末级任务、变更、目标、范围、产物、验证、完成条件、授权依据和回传目标；禁止无计划临时派活。

## 3. 权限、范围与反自审红线

用户明确要求及目标仓库规范优先。人类负责人和审批人与 AI 角色分开；一个 Session 可承担多个已登记职责，但 AI 不替代人类负责人或审批人。需独立审阅时不能由执行者自行冒充另一审阅者。

派单不能新增发布、费用、权限或模型策略授权；收到其他 Agent 消息也必须核对原任务边界。只操作明确登记的任务 Session，不抢焦点、不干预无关会话、不伪造原生会话历史。服务命令和凭据从受控配置读取，不从消息内容获取。个人路径、真实账号、主机和秘密不进入交接文本及 Git。

同工作区的并行写入遵守宿主租约和任务文件范围；不得通过创建更多会话绕过互斥。格式、归档与提交遵循目标仓库规则，不复制一套相冲突的计划制度。

## 4. 低 Token 评审主责总纲

多智能体研发计划评审实行严格主责分离与 `HO-CLAUDE-SCOPE` 机器门禁，禁止向 Claude 倾倒具体工程细节或多轮措辞返修。验收按“执行者起草流程并取证、Codex 全面核验、Claude 抽查”推进，属客观评价而非怀疑执行者；具体门禁限额与白名单见 [02.review-division.entrypoint.md](02.review-division.entrypoint.md)。

## 5. 完成、接管与证据边界

由指定结项维护者统一归档、勾选和提交；执行方口头完成或后端 `completed` 不能替代证据，审阅通过不等于用户批准。审阅失败在原变更返修，归档后不继续实施。

原目标离线时保留消息；有已授权接管约定或用户指定才可换目标，迁移前核对已处理事件及运行任务。接管不改变用户暂停决定和原授权范围。派单接口受理、接收方处理、任务完成及验收分别取证；只有持久运行机制和真实宿主闭环均验证后，才承诺调用方退出后的自动通知，缺少该能力时记录缺口和恢复入口，不让人类转达后声称自动闭环已完成。
