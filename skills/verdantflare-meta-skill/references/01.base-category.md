# 技能统一结构与分类设计

## 1. 当前依据

- [入口](../SKILL.md)：范围与按需读取协议。
- [规则约束](01.base-rules.md)：入口与专册的内容归属和体积上限。

## 2. 统一目录结构

所有技能采用同一结构，不再按复杂度自选布局。技能根目录只允许 `SKILL.md` 一份 Markdown，其余文档进入 `references/`：

```text
<skill-name>/
├── SKILL.md                     入口：范围与边界、按任务读取、工具与命令
├── references/
│   ├── 01.base-category.md      分类与边界
│   ├── 01.base-workflow.md      执行流程
│   ├── 01.base-rules.md         规则约束
│   ├── 01.base-acceptance.md    验收标准
│   ├── Cx.<slug>-<维度>.md       可选：分支矩阵专册
│   └── <主题>.md                可选：安装、数据格式、接口等主题专册
├── scripts/                     可选：脚本与测试
└── resources/ 或 assets/        可选：模板、样例与静态资源
```

四份底座对任何技能都必备。单路径的小技能也写四份，每份可以只有几行；这样任何人打开任何技能，都能在同一位置找到规范、流程与验收，不必猜测写在入口哪一节。

## 3. 四维职责

| 底座专册   | 只写什么                                                           |
| :--------- | :----------------------------------------------------------------- |
| 分类与边界 | 适用与不适用输入、场景或分支划分、取证探针与分类判据、分支索引     |
| 执行流程   | 前置条件、输入输出、步骤、完整命令与参数、失败恢复、交接产物       |
| 规则约束   | 硬约束、默认值与可调条件、例外、存储与命名契约、规则来源和更新条件 |
| 验收标准   | 完成与失败条件、测量流程、文字评分规则与数据评分准则、门禁、报告   |

阈值只在一处定义，其他位置引用。同一条信息只归一个维度，跨维度时按“决定能不能做”归规则、“决定怎么做”归流程、“决定做得对不对”归验收。

## 4. 分支矩阵

多个分支在四个维度都有独立差异时，按分支追加 `Cx.<slug>-category.md`、`-workflow.md`、`-rules.md`、`-acceptance.md` 四份专册，例如 `C1.local-workflow.md`。分支编号唯一，slug 使用小写英文、数字与短横线；分支一旦建立必须四维齐全，共享内容留在底座，分支只写差异。差异只在一两个维度时不建分支，直接写在底座对应小节。

- 分类：[底座](../resources/templates/01.base-category.template.md)、[分支](../resources/templates/Cx.slug-category.template.md)
- 流程：[底座](../resources/templates/01.base-workflow.template.md)、[分支](../resources/templates/Cx.slug-workflow.template.md)
- 规则：[底座](../resources/templates/01.base-rules.template.md)、[分支](../resources/templates/Cx.slug-rules.template.md)

## 5. 数据驱动分类设计准则

技能需要对来源不确定的输入自动分流、且分错会导致下游出错时，分类专册满足以下三项；按用户明说的任务类型分支时，写清各分支边界即可，不生造分类器：

1. **定义前置取证步骤**：写明分类前执行的自动检查或探针，例如读取元数据、解析结构、统计内容特征、比对参照样本，并把提取的特征落盘为结构化清单便于复核。
2. **给出可验证的分类判据**：每个分支写明数值边界或布尔组合条件，能由脚本或检查项复现，不依赖文件名或主观印象；判据覆盖不到的输入定义兜底分支或人工确认路径。
3. **分类确定性绑定下游**：每个分类一对一或按明确条件映射到具体流程、工具与参数预设；不影响下游处理的分类合并或删除。
