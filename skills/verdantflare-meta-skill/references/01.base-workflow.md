# 技能新建、整改与经验沉淀流程

## 1. 当前依据

- [结构与分类](01.base-category.md)：统一目录与四维职责。
- [规则约束](01.base-rules.md)：入口与专册的内容归属。
- [验收标准](01.base-acceptance.md)：静态、行为和人工结果分离。

## 2. 工具命令

命令在本技能安装目录运行，目标目录可以是任意项目；从其他目录执行时使用本技能脚本的实际路径。

```text
python -m pip install -r scripts/requirements.txt
python -X utf8 scripts/lint_skill.py init /path/to/new-skill
python -X utf8 scripts/lint_skill.py init /path/to/new-skill --categories C1.local,C2.remote
python -X utf8 scripts/lint_skill.py lint /path/to/target-skill
python -X utf8 scripts/lint_skill.py lint /path/to/target-skill --style numbered
python -X utf8 scripts/lint_skill.py lint /path/to/target-skill --allow-placeholders
python -X utf8 -m unittest discover -s scripts -p test_lint_skill.py
```

- `init` 生成入口与四份底座；加 `--categories` 时追加分支四维专册与入口路由行。已存在文件一律保留，不改写存量入口，追加分支后手工合并路由表。
- `lint` 默认执行全部结构检查；`--style numbered` 追加标题编号检查；`--allow-placeholders` 只用于骨架阶段，报告标记为未完成。

## 3. 新建技能

1. 先写能力、触发条件和排除边界，确认确实需要技能而不是项目文档。
2. 运行 `init` 生成骨架，按[四维职责](01.base-category.md#3-四维职责)填写四份底座，再填写入口三节。
3. 运行 `lint` 直到通过，再按验收专册做行为验证。

## 4. 整改存量技能

入口超限、缺底座或根目录有多余 Markdown 的技能按以下步骤整改。整改只搬移与精简，不改变执行行为；搬移中发现的规则冲突或过时内容登记为待确认项，不顺手改规则。

1. **盘点**：运行 `lint` 记录全部错误；列出入口每个章节与根目录、`references/` 下每份文件，逐段标注应归入的维度（分类、流程、规则、验收）、主题专册，或应删除的历史与重复内容。
2. **搬移**：按标注把正文移入对应底座；已有命名不合规的专册（如 `workflow.md`、`acceptance.md`）重命名为底座名称或合并进底座；`FAQ.md`、`lessons.md` 拆进流程的失败恢复与规则的例外，纯试错叙述移到项目归档文档。
3. **重写入口**：按模板改写为三节，路由表覆盖全部专册。
4. **修引用**：搜索仓库内对旧章节锚点与旧文件名的链接（计划、变更、其他技能、脚本输出提示），逐一更新。
5. **验证**：`lint` 通过；比对整改前后关键约束、阈值与命令无遗漏；运行技能自带测试。

## 5. 经验沉淀（先验证、再沉淀）

凡新增或改变分类判据、流程步骤、阈值或硬约束，按以下闭环执行；纠错字、修链接、调格式等不改变行为的修订直接处理。

1. **界定分类与取证方法**：分析新问题为何在旧流程中漏检或做错，提炼能前置识别该类任务的取证步骤与分类判据。
2. **设计流程与配套改动**：为该分类设计端到端处理流程；涉及配置基线或脚本改造时一并纳入版本管理。
3. **用真实案例验证**：选典型真实案例走通取证、执行、测量与评审，在项目惯用位置留下可追溯记录（变更文档、Issue、PR 或测试报告）；需要人工结论的环节按项目已有审批方式取得真实确认。
4. **通过后再沉淀**：只把通过验证的判据、步骤、评分规则写入对应底座；试错过程留在项目文档，未验证的推测记为待验证项。

每条拟沉淀规则应能回答：来源与证据是什么；适用于哪些任务、输入、工具版本或环境；是硬约束、默认值还是个人偏好；有哪些例外；什么条件下更新或废弃。

## 6. 评审与交付

评审直接给出按严重程度排序的发现、位置、影响和建议，不初始化或改写被审对象；结构不合规本身即为发现项。修订保留目标名称与已有有效内容。

交付报告说明修改范围、已执行验证、尚未验证事项，以及是否实际安装或发布。静态通过不代表用户批准，也不证明业务结果正确。全局沉淀先确定唯一维护源，安装按[安装与接入](install.md)执行。
