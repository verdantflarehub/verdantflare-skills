# Grok 派单、高清化重置监控与 AFK Pilot 同步（01.dispatch）

## 1. 输入与输出

- **输入**：明确的工作目录绝对路径 `cwd`、新的 `request_id`、`mode`（默认 `acp`，可选 `headless`）、包含目标/输入素材或代码路径/输出位置/尺寸格式规范/验证要求的 `prompt`；可选已有 `session_id`（或 `thread_id`）、续接与取消的 `task_id` 与 `expected_turn_id`，或全局安装参数。
- **输出**：持久任务编号 `task_id`、会话编号 `session_id`、轮次编号 `turn_id`、增量事件流、`content_json`（含 `answer`、`media`、`file_changes`、`commands`、`afk_pilot_synced`）、`~/.grok/sessions/` 轨迹与 `session-meta.json` 索引，或同步至 `~/.agents/skills/verdantflare-agent-grok/` 的全局安装副本。
- **技能入口**：[SKILL.md](../SKILL.md)。

## 2. 分类

将有明确工作目录、输入素材、高清化或修改目标及验收标准的任务交给 Grok（古若科），专职系统图片、地图、界面素材重置高清化，以及受授权的工作区辅助研发任务。

- **`acp`（默认推荐）**：通过 `grok.exe agent --no-leader stdio` 运行 JSON-RPC 2.0 ACP 会话（`session/new`、`session/load`、`session/prompt`），生成非 `headless` 的标准会话目录（`summary.json`、`chat_history.jsonl`、`updates.jsonl`），并同步更新 `~/.grok/client-state/session-meta.json`，确保会话在 VS Code **AFK Pilot** 的 `grok.chat`（Recent）和 `grok.projects`（Projects）面板直接展示与点击回放。
- **`headless`**：调用者显式指定的无头单次模式（`grok.exe -p --output-format json`）。因 `summary.json` 会标记 `session_kind="headless"`，AFK Pilot 默认将其归入后台隐藏，不用于需要面板展示的任务。

`grok_capabilities` 返回 CLI 与 AFK Pilot 扩展版本、会话列表、`afk_pilot_visible` 与 `afk_pilot_registered` 状态。

当前适配面向 Windows、Grok CLI（`~/.grok/bin/grok.exe`）与 VS Code 扩展 **AFK Pilot**（`pawelhuryn.grok-vscode-phuryn-*`）。运行时跳过 `.obsolete` 动态探测最新有效扩展版本，不锁定单一扩展号；服务为本机 `stdio`，不提供公网监听。认证由 `~/.grok/config.toml` 或环境变量管理，技能文件不保存 API 密钥，也不把凭据写入任务参数。

## 3. 工作流

### 3.1 全局安装与接入检查

首次部署或源码修改后，运行 [install.py](../scripts/install.py) 同步全局技能、构建独立虚拟环境运行时并向对端智能体注册 MCP（仅同步技能时省略 `--register-mcp`）：

```powershell
python -X utf8 scripts/install.py --replace --register-mcp
python -X utf8 scripts/launch.py --call grok_capabilities
```

确认宿主 MCP 列表包含 `verdantflare-agent-grok`。配置入口由 `VERDANTFLARE_AGENT_GROK_SERVICE` 指定，默认从用户数据目录的 `verdantflare-agent-grok/service.json` 读取。运行 `grok_capabilities`，必要时传入 `cwd` 与分页 `cursor`，检查 `acp="read_verified"`、`afk_pilot_ui="read_verified"` 及现有会话列表。

### 3.2 任务交接与派单

交接文本至少包含目标、输入素材或代码路径、输出位置、尺寸/格式规范和验证要求。调用 `grok_task_start`，传入新的 `request_id`、`mode="acp"`、绝对 `cwd` 与 `prompt`；如需在既有会话上直接启动，可传入 `session_id`（或 `thread_id`）。保存返回的 `task_id` 与绑定后的 `session_id`。通信超时后先查原任务或用同一 `request_id` 重试，不另造编号重发。

### 3.3 查询、结果、续接与取消

- **查询进度（`grok_task_status`）**：查询状态、`session_id`、`turn_id` 与增量事件（含 `afk_pilot_synced`、`assistant_text`、`tool_call`）；下次携带 `after_event` 接续读取。
- **读取结果（`grok_task_result`）**：进入终态后调用，解析 `content_json`，检查 `answer`、`media`（生成的图片/视频路径）、`file_changes`、`commands` 与 `afk_pilot_synced`。在 VS Code **AFK Pilot** 面板（`grok.chat` 或 `grok.projects`）可直接打开对应会话查看完整对话与工具调用轨迹。
- **续接任务（`grok_task_continue`）**：需要 `task_id`、新的 `request_id`、`prompt` 和上一轮 `expected_turn_id`。底层通过 ACP `session/load` 加载原 `sessionId` 续接，并刷新 `session-meta.json` 的 `activeAt` 时间戳。
- **取消轮次（`grok_task_cancel`）**：必须携带当前 `expected_turn_id`，底层发送 ACP `session/cancel` 通知并安全收敛为 `cancelled`。

### 3.4 失败恢复与 CLI 派单

`SESSION_BUSY` 表示工作区父子目录租约或目标 `session_id` 正在执行任务，等待当前任务完成或切换隔离工作区。CLI 派单需要 `--wait` 让后台执行进程保持存活直到当前轮次完成：

```powershell
python scripts/launch.py --call grok_task_start --arguments task.json --wait
python scripts/launch.py --call grok_task_status --arguments status.json
```

## 4. 规范

1. **授权与权限**：上游任务授权与视觉母版人工审定分别记录。首轮基准母版必须先经人工审定通过，严禁未经审定直接批量衍生。`acp` 模式面向后台无人值守派单，默认启用 `--always-approve` 并在收到 `session/request_permission` 时自动选择 `allow` 放行工具调用；人工接管交互在 AFK Pilot 面板内完成。禁止递归委托同一个服务（向子进程注入 `VERDANTFLARE_AGENT_GROK_DEPTH=1` 并在入口硬拦截，同时附加防递归提示词前缀）。
2. **参数与幂等**：提示词非空且 UTF-8 不超过 64 KiB；任务超时为 30～86400 秒，默认 3600 秒；未知字段直接拒绝。同一 `request_id` 与相同参数幂等返回原任务；相同 `request_id` 不同内容报 `REQUEST_CONFLICT`。ACP 会话通过 `session/load` 恢复，`headless` 使用 `--resume`；`--session-id` 只表示新会话 ID，不用于续接。续接和取消绑定 `expected_turn_id`，过期轮次报 `STALE_TURN`。
3. **工作区、存储与 AFK Pilot 同步**：工作目录须为有效绝对路径（配置 `allowed_roots` 为 `["*"]` 或 `[]` 时支持任意绝对工作区路径；配置具体路径列表时限定在允许根内），按真实路径校验父子目录写任务互斥与同一 `session_id` 租约互斥，`interrupted_unknown` 同样保留占用，不能以 `cancel` 无证据释放。新建和续接受理后固定由该连接 worker 领取；仅原命令未领取时可以在 owner 丢失后恢复。`acp` 模式下，服务在 `initialize` 阶段将 `clientCapabilities.fs` 与 `terminal` 声明为 `false`，使 `grok.exe` 使用内置工具直接落盘 `~/.grok/sessions/<urlencoded-cwd>/<sessionId>/`，并由服务原子更新 `~/.grok/client-state/session-meta.json`（保留用户自定义的 `customName` 与 `pinned` 字段）。ACP 结果的 `file_changes` 不包含 `kind=read/search` 或工具元数据 `read_only=true` 的路径；只读访问不能作为越界写入证据；原生轨迹、实际文件差异和结果摘要分别核对。
4. **兼容与维护**：当前规则基于 Grok CLI `1.0.77` ACP stdio 协议与 VS Code 扩展 `pawelhuryn.grok-vscode-phuryn` `4.15.8` 实测；扩展或 CLI 升级后须重新运行探测脚本校验会话目录结构与 `session-meta.json` 字段。技能源码在仓库 `skills/verdantflare-agent-grok/` 唯一维护，安装副本更新通过安装脚本同步；公开文档严禁写入本机绝对路径、用户名或 API 密钥。

## 5. 验收

- **静态与协议验证**：技能结构检查（含隔离目录）、Markdown 检查、自包含单测（使用运行时虚拟环境 Python 执行 `-m unittest discover -s scripts -p "test_*.py"`）及安装文件全量 SHA-256 哈希比对通过。标准 MCP 客户端能够初始化、列出七项工具、调用 `grok_capabilities`；非法字段、超限提示词和错误编号返回结构化错误码。
- **行为与 AFK Pilot 展示验证**：使用 `acp` 模式完成提交（`grok_task_start`）、查询（`grok_task_status`）、结果（`grok_task_result`）与续接（`grok_task_continue`）闭环，核对三项落盘证据：
  1. `~/.grok/sessions/<urlencoded-cwd>/<sessionId>/` 下存在 `summary.json`、`chat_history.jsonl`、`updates.jsonl`，且 `summary.json` 的 `session_kind` 不为 `"headless"`。
  2. `~/.grok/client-state/session-meta.json` 中存在对应 `<sessionId>` 条目，且 `provider="grok"`、`providerCwd` 与 `activeAt` 已更新。
  3. `grok_capabilities` 返回该会话 `afk_pilot_visible=true` 且 `afk_pilot_registered=true`。
- **业务完成判定与交付记录**：任务完成须同时满足约定产物存在、内容与尺寸符合规范、验证命令通过且无未解决问题，模型口头声明不能代替真实文件校验。技能可见、MCP 已注册、真实工具可调用、AFK Pilot 会话同步和人工确认分别报告；跨智能体接入须至少由另一个宿主或 CLI 调用实测留证。交付记录包含 CLI 与 AFK Pilot 版本、运行模式、任务与会话编号、产物位置、验证结果及人工结论；公开报告脱敏账号、密钥和本机个人路径。
