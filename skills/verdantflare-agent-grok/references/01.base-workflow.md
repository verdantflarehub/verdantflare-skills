# 执行流程

## 1. 接入检查

确认服务已安装，宿主 MCP 列表包含 `verdantflare-agent-grok`。配置入口由 `VERDANTFLARE_AGENT_GROK_SERVICE` 指定，默认从用户数据目录的 `verdantflare-agent-grok/service.json` 读取。

运行 `grok_capabilities`，必要时传入 `cwd` 与分页 `cursor`，检查 `acp="read_verified"`、`afk_pilot_ui="read_verified"` 及现有会话列表。

## 2. 任务交接与派单

交接文本至少包含目标、输入素材或代码路径、输出位置、尺寸/格式规范和验证要求。调用 `grok_task_start`，传入新的 `request_id`、`mode="acp"`、绝对 `cwd` 与 `prompt`；如需在既有会话上直接启动，可传入 `session_id`（或 `thread_id`）。

保存返回的 `task_id` 与绑定后的 `session_id`。通信超时后先查原任务或用同一 `request_id` 重试，不另造编号重发。

## 3. 查询、结果与面板展示

使用 `grok_task_status` 查询状态、`session_id`、`turn_id` 与增量事件（含 `afk_pilot_synced`、`assistant_text`、`tool_call`）；下次携带 `after_event` 接续读取。

进入终态后调用 `grok_task_result`。解析 `content_json`，检查 `answer`、`media`（生成的图片/视频路径）、`file_changes`、`commands` 与 `afk_pilot_synced`。在 VS Code **AFK Pilot** 面板（`grok.chat` 或 `grok.projects`）可直接打开对应会话查看完整对话与工具调用轨迹。

## 4. 续接与取消

`grok_task_continue` 需要 `task_id`、新的 `request_id`、`prompt` 和上一轮 `expected_turn_id`。底层通过 ACP `session/load` 加载原 `sessionId` 续接，并刷新 `session-meta.json` 的 `activeAt` 时间戳。

`grok_task_cancel` 必须携带当前 `expected_turn_id`，底层发送 ACP `session/cancel` 通知并安全收敛为 `cancelled`。

## 5. 失败恢复

`SESSION_BUSY` 表示工作区父子目录租约或目标 `session_id` 正在执行任务。等待当前任务完成或切换隔离工作区。

CLI 派单需要 `--wait` 让后台执行进程保持存活直到当前轮次完成：

```powershell
python scripts/launch.py --call grok_task_start --arguments task.json --wait
python scripts/launch.py --call grok_task_status --arguments status.json
```
