# 变更文档规范

## 1. 职责与位置

一份变更承载一个独立子任务的实施、执行证据与结项，在子任务开始执行时新建，并回填计划中该任务的关联进展链接。进行中变更放 `docs/changes/change_YYYYMMDD_<动作与对象>.md`，完成后移入 `docs/archive/changes/`。同一任务的调试与反馈继续更新原变更，不按文件、对话轮次或单条反馈拆分，也不提前结项；范围外的新需求回到计划另列子任务，另建变更执行，不在原变更无限追加范围。

文首包含负责人、助手及职责、状态、创建日期，以及所属计划链接（有计划时）。负责人默认沿用所属计划，用户另行指派时按指派填写；无计划的直接任务同样须有负责人。AI 只登记为助手，不写为负责人或审批人。

## 2. 内容结构

推荐章节：当前依据、问题与目标、修改范围、执行记录、验证证据、结项条件。执行记录每条注明实际执行的助手；命令、结果及证据写在对应小节，避免长表格。

- 修改范围说明具体对象、行为变化和影响边界。
- 执行记录保存实际操作、关键结果及当前停点。
- 验证证据列出检查环境、命令、结果及可追溯路径，区分未执行、失败与通过。
- 中断时记录阻塞原因、外部任务标识和恢复条件；恢复时先读变更，核对工作区与外部任务标识再接续，避免重复提交任务。
- 结项核对预设完成条件，分别记录技术验证、必要人工检查及提交同步状态。

## 3. 完成与归档

不以静态检查替代业务验收，不把 AI 检查写为用户批准；未执行的远端或目标环境测试不记为通过。修改上线后逐项对照批准的原型与设计，记录已还原项、数据差异、缺项与验收证据。条件满足且证据齐备后标记已完成，立即移至 `docs/archive/changes/`，保留文件名，更新所属计划与其他引用。归档后不再继续实施，新需求另建变更。

归档属于交付内容，移动后对最终文件执行格式化及链接检查。提交和推送遵循已有授权与仓库流程，不能因为运行 Format 就提前提交。
