# 设计文档规范

## 1. 职责与结构

设计文档描述问题、目标、约束、方案与关键取舍。先核对现有实现和用户需求，明确现状与拟议方案，不把设计假设写成已上线事实。

推荐章节：当前依据、背景与目标、范围与非目标、现状及约束、方案与关键契约、验证方法、风险与待决事项。按实际复杂度裁剪；仅保留影响实现和评审的内容。

## 2. 业务要求

“当前依据”逐条链接需求、代码、接口或已有文档并说明用途。涉及接口、数据、状态流或异常路径时，明确输入输出、失败行为、兼容边界与迁移条件。

备选方案记录取舍理由和证据；未确定的关键问题集中列出。技术流程图用短节点，定义和判据写在图下。目标仓库规定文档编码与图表编号时从其规定。

## 3. 验收与归档

检查每项目标是否有对应方案和可执行验证方法；核对与实现的差异，区分设计结论、实测结果与待验证假设。执行进度放关联计划或变更，不持续追加到设计正文。

活跃设计放 `docs/`；完成历史使命或被替代后移入唯一归档根 `docs/archive/`，保留内容并修复引用。
